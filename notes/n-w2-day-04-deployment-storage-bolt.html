1. 입력 폼 필드 정의서

무엇을 했나

같은 신청 폼(이름, 소속, 이메일, 휴대폰 등)을 각자 정의서로 만들어 보는 실습이었습니다. 한 시트 안에 강사님 예시 탭과 수강생 탭이 나란히 있어서, 같은 폼도 사람마다 정의하는 깊이가 다르다는 점을 바로 비교할 수 있었습니다.

기본 열

열내용

제목필드 이름 (이름, 이메일 등)
유형입력필드, 선택박스, 체크박스, 드롭다운, 장문 입력필드
필수 또는 선택비워도 제출되는지 여부
특이사항입력 가능 문자, 형식 같은 기본 규칙

내 정의서 예시 (일부)

기본 열만으로는 "이렇게 입력하면 어떻게 되는데?"에 답할 수 없어서, 글자 수, 검증 규칙, 예외사항, 피드백 열을 더 붙였습니다. 시트에서 읽히는 부분만 옮겼고, 길어서 잘린 칸은 생략했습니다.

예외 하나마다 결과(막을지, 자동으로 고칠지)와 안내 위치(입력칸 아래, 팝업)까지 적어야 정의서가 끝난다는 점이 이번 실습의 핵심이었습니다.

다른 정의서에서 본 방식

같은 폼이라도 정의서를 쓰는 방식이 여러 가지였습니다.

  1. 글자 수 제한, 기능 제한 사항, 기능별 대응을 열로 나누기 (오류가 난 필드는 하단에 빨간 안내 문구)
  2. 기존 기능과 예외 사항을 열로 나누고, 예외에 번호 붙이기
  3. 개인정보 동의를 체크하지 않으면 신청 버튼을 비활성화하거나 안내 문구 보여 주기
  4. 참석 인원처럼 숫자 범위(1~10명)와 기본값을 정하고, 남기실 말씀에는 글자 수 표시(0/500) 넣기
  5. 다음 단계로 넘어가는 트리거를 정의하기

3. 배포하기

왜 배포하나

로컬에서만 확인하면 팀원이 볼 수 없습니다. 배포하면 주소 하나로 팀 안에서 공유할 수 있습니다. 오늘 수업의 질문도 "우리 사이트를 외부 사용자가 어떤 경로와 채널로 들어올까"였습니다.

Netlify Drop

  1. app.netlify.com/drop 에 접속합니다.
  2. 폴더, zip 파일, html 파일 하나를 끌어다 놓습니다.
  3. 몇 초 뒤 인터넷 주소가 생깁니다. 일부 주소는 비밀번호가 필요했고, 비밀번호는 접속 화면에 안내되어 있었습니다.
  4. 새 프로젝트를 만들어 올려 보고, 기존 프로젝트에 새 파일을 올려 업데이트도 해 봅니다.
  5. 올린 페이지를 크롬에서 우클릭, 검사로 열고 모바일 반응형 화면으로 바꿔서 봅니다.
  6. 카카오톡 나에게 보내기로 링크를 보내고, 카카오톡에서 눌렀을 때 잘 보이는지 확인합니다.

  2. Vercel에서 새 프로젝트를 만들고, GitHub 계정으로 로그인해 저장소를 이름으로 찾아 가져옵니다(import).
  3. 설정을 바꾸지 않고 Deploy를 누르면 최종적으로 vercel.app 주소가 생깁니다.

4. 신청 내용은 어디에 저장될까

질문

강사님의 질문은 "현재 아티팩트에는 사용자가 신청서에 입력한 내용이 어디에 저장되는가?"였습니다.

저장 방식 세 가지 비교

교안의 비교표를 정리했습니다.

저장 방식신청 직후새로고침다른 브라우저나 기기
메모리(변수)화면에는 보이지만 저장소는 비어 있음사라짐안 보임
브라우저 저장소(localStorage)화면에 보이고 저장소에 줄이 생김남음안 보임
서버 데이터베이스화면에 보이고 서버에 저장남음보임

같은 크롬이어도 시크릿 창이나 다른 배포 주소(Netlify 주소와 Vercel 주소)에서는 저장 공간이 따로라 보이지 않습니다.

제가 만든 이벤트 신청 폼 실습 기록

수업 질문에 맞춰 제 신청 폼을 단계별로 고쳐 보았습니다.

단계바꾼 것
1에러 메시지를 빨간색으로 바꾸고, 오류가 난 입력칸 테두리도 빨간색으로 표시
2신청하기를 누르면 폼 화면이 사라지고 별도의 완료 화면 보여 주기
3처음에는 입력한 내용이 어디에도 저장되지 않는다는 것을 확인
4신청 내용을 브라우저에 임시 저장하고, 신청 명단 조회와 전체 삭제 버튼 추가
5휴대폰 번호를 필수로 변경
6중복 신청이 어떤 조건으로 판단되는지 코드로 확인

저장 방식에서 확인한 한계입니다.

  1. 신청 명단이 그 브라우저에만 있어서, 여러 사람이 신청하는 이벤트의 실제 접수 명단으로는 쓸 수 없습니다. 연습과 시연용입니다.
  2. 명단 버튼이 신청자에게도 보이면, 같은 컴퓨터를 쓰는 다음 사람이 앞 사람의 이름과 연락처를 볼 수 있습니다.
  3. 브라우저 데이터를 지우면 명단도 사라집니다.
  4. 입력규칙표(정의서)에는 휴대폰이 선택으로 적혀 있는데 폼에서는 필수로 바꿔서, 서로 맞춰야 합니다.

중복 신청은 어떻게 판단했나

  1. 입력값 검사를 모두 통과한 뒤에 중복 검사를 합니다.
  2. 입력한 휴대폰 번호가 저장된 명단에 이미 있으면 중복으로 보고 접수하지 않으며, "이미 신청된 번호입니다." 팝업을 띄웁니다.
  3. 판단 기준은 휴대폰 번호 한 가지입니다. 이름이나 이메일은 보지 않습니다.
  4. 번호는 숫자만 남기고 0XX-XXXX-XXXX 모양으로 자동 통일하기 때문에, "0XX-XXXX-XXXX"과 "0XX-XXXX-XXXX"은 같은 번호로 비교됩니다.
  5. 한계는 두 가지입니다. 번호가 다른 같은 사람은 걸러지지 않고, 다른 브라우저에서 신청한 번호와는 비교할 수 없습니다.

개발자 도구에서 저장값 보기

  1. 크롬에서 우클릭, 검사로 개발자 도구를 엽니다.
  2. 위쪽 Application 탭을 누르고, 왼쪽 Storage의 Local storage 아래 내 사이트 주소를 누릅니다.
  3. 신청을 넣으면 오른쪽 표에 줄이 생기고, 줄을 누르면 저장된 내용이 펼쳐집니다.

수업에서는 아래 세 가지를 직접 확인하라고 안내받았습니다.

  1. 새로고침해도 남아 있는가
  2. 강제 새로고침(저장된 파일을 무시하고 다시 불러오는 새로고침)해도 남아 있는가
  3. 새 브라우저 창을 띄워 같은 주소로 들어가도 보이는가

3번이 잘 안 되는 경우에는 지금 로그인된 브라우저 자체를 확인해 보라는 안내가 있었습니다. 저장된 이름과 연락처가 글자 그대로 보이기 때문에, 브라우저 저장소에는 실제 개인정보를 넣지 않는 것이 안전합니다.

5. 볼트(bolt.new)

볼트란

말로 요청하면 웹 앱을 만들어 주는 AI 앱 빌더입니다. 화면 만들기, 데이터베이스, 공개(배포)를 한곳에서 할 수 있습니다. 이전에는 파일을 내려받아 깃허브에 올려야 했지만, 볼트는 만들기부터 공개까지 한 화면에서 합니다.

오늘 흐름

단계한 일확인할 것
1Hello 문구, 이름 입력칸 하나, 저장 버튼만 있는 페이지를 최소한의 디자인으로 만들어 달라고 한 줄 요청미리보기에 세 가지가 보이는지
2입력한 이름이 볼트 데이터베이스에 저장되게 연결해 달라고 한 줄 요청Database 화면의 표에 이름이 한 줄 생겼는지
3Publish로 공개하고 휴대폰에서 다른 가상 이름 저장컴퓨터의 Database 화면에 줄이 늘었는지

알아 둘 점

  1. "저장되었습니다" 문구만 믿지 않고 데이터베이스 화면을 열어 직접 확인합니다. 표 목록에는 0 rows로 보여도 표를 열면 있을 수 있습니다.
  2. 공개한 주소는 누구나 열고 이름을 넣을 수 있어서 가상의 이름만 넣습니다.
  3. 무료로 공개한 사이트에는 "Made in Bolt" 표시가 붙습니다.
  4. 교안 기준(강사님 확인 2026-11-05)으로 무료 계정은 하루 토큰 한도가 있고, 남은 양은 다음 날로 넘어가지 않습니다. 변동될 수 있어서 공식 화면에서 다시 확인하는 것이 좋습니다. 그래서 프롬프트는 짧게 쓰고, 고칠 것은 모아서 한 번에 보냅니다.
  5. 데이터베이스 연결은 화면만 만들 때보다 토큰을 더 씁니다.
  • 볼트: https://bolt.new

6. 오늘 느낀 점

  • 필드 정의를 더 체계적이고 상세하게 하는 방법을 배웠습니다.
  • 개발한 결과를 로컬에서만 확인해야 해서 팀에 공유하기 어려워 고민한 적이 많았는데, Netlify는 그럴 때 정말 좋은 도구인 것 같습니다.
  • 볼트는 처음 써 봤고, 개발과 데이터베이스, 배포까지 한 번에 되는 편한 올인원 도구인 것 같습니다.
  • 개발자 도구에서 저장값을 확인할 수 있다는 것도 처음 알았습니다.

8. 교안에서 더 읽어 볼 것

아래는 같은 교안에 있는 내용입니다. 오늘 수업에서 어디까지 진행했는지 확인되지 않아 참고용으로만 적습니다.

  1. 도구를 고르는 세 기준: 원본 코드가 어디에 저장되나, 어디서 실행되나, 어디까지 대신 해 주나. 도구 이름 대신 기준으로 보면 새 도구가 나와도 비교할 수 있습니다.
  2. 신청 데이터 정의: 입력, 저장, 삭제, 기본 데이터로 나누어 적습니다. 기본 데이터는 사용자가 아무것도 하기 전에 시스템에 이미 있어야 하는 값입니다.
  3. 콘솔 로그: 저장 성공은 console.log, 중복 같은 주의는 console.warn, 형식 오류 같은 실패는 console.error로 남겨 개발자 도구에서 읽습니다. 로그에 이름과 연락처 같은 개인정보는 남기지 않습니다.
  4. index.html 한 파일로 만드는 이유: PM 프로토타입은 파일 하나로 보내고 올리기 쉽고, 실제 서비스는 개발자가 파일을 나누어 다시 만듭니다.
  5. 시안 3개 비교: 시안을 고르는 기준은 취향이 아니라 PRD의 가설입니다.
