2. 세션별 정리

SESSION 1 · 사용자 흐름과 실패·예외 시나리오 (09:20–10:40) [교안]

  • 순서: 집중할 사용자 고르기 → 시나리오 쓰기 → 한 줄에 행동 하나로 쪼개기 → 실패·예외 찾기 → 안내 문구 정하기
  • 핵심: 실패·예외는 새 화면보다 같은 화면의 다른 상태(오류 문구, 빈 상태, 마감 안내)로 보여 주는 경우가 많다.
  • 교안 예시(셀렉트마켓 연말 이벤트): 성공 흐름 9단계 + 실패·예외 4가지(연락처 형식 오류, 동의 안 함, 중복 신청, 마감 지남)
  • 실험: 예외 표 없이 "신청 폼 만들어 줘"만 요청하고, 빈칸으로 '사전 신청'을 눌렀을 때 '완료'가 뜨는지 확인한다.
  • 성공 기준: 흐름 표의 줄마다 행동이 하나씩이고, 예외 표의 모든 줄에 안내 문구가 있다.

강사 화면 제시 자료 — 유즈케이스 다이어그램 [실습, 원 출처 확인 불가]

  • 액터 1명("읽기") + 기능 3개(도서 빌려보기, 도서 반납, 벌금을 내다)
  • "벌금을 내다"가 <<extend>> 점선으로 "도서 반납"에 붙어 있음
  • extend: 라면에 "계란 추가"처럼, 기본 흐름에 가끔만 붙는 선택 기능
  • 한계 [추정]: 액터 이름 "읽기"는 사람이 아니라 행동이라 "독자·이용자"의 오기일 가능성이 있음. 수업에서 정정이 있었는지는 확인 불가. 벌금이 생기는 조건(반납일 초과)은 그림에 없어 시나리오 표의 예외 줄에 따로 써야 함.
  • 이 그림은 "누가 어떤 기능을 쓰는가"의 관계도이고, 교안의 사용자 흐름 표(한 줄에 행동 하나)와는 형식이 다름.

SESSION 2 · IA와 간단 PRD v1 (10:40–12:00) [교안]

  • IA 만드는 법: 사용자 흐름의 화면명을 모아 중복을 지우면 필요한 화면 목록이 나온다. 이를 위계로 정리한 것이 IA.
  • PRD 구성: 개요 / 문제 / 가설·지표 / IA / 유즈케이스 / 핵심 기능 / 확인 필요
  • 지표 2개 (월요일 확정분): 핵심 = 신청 고객 중 이벤트 기간 구매율 / 보조 = 방문 대비 신청 완료율(교안 예시 목표 20%)
  • 실험: 프롬프트에서 "지어내지 말고 '확인 필요'로 표시해"를 지우고 다시 보낸다. 내가 정한 적 없는 내용(운영자 화면, 알림 방식 등)이 들어오는지 본다.
  • 성공 기준: 점검에서 X가 0개이고, 지표 칸에 핵심·보조 지표가 모두 있다.

SESSION 3 · PRD로 클로드 디자인 시안 3개 비교 (13:00–14:20) [교안]

  • 시안을 고르는 기준은 취향이 아니라 PRD의 가설(혜택 확인 → 신청 행동을 하게 만드는가).
  • 평가 기준 4개(1~3점): 혜택이 첫 화면에 보이나 / 신청까지 스크롤이 짧나 / 예외 문구 자리가 있나 / 휴대폰에서 읽기 쉬운가
  • 교안 예시 결과: A 혜택 강조형 10점(선택), B 신청 폼 우선형 9점, C 선물 카테고리형 8점
  • 들어가는 길: claude.ai/artifacts/design → 디자인 시스템을 물으면 '없이 진행'
  • 막히면: 시안이 색만 다르면 '시안 방향' 칸을 더 구체적으로 적어 다시 요청

SESSION 4 · 프로젝트와 지침 (14:20–15:20) [교안]

  • 프로젝트에 PRD를 자료로 넣고 지침을 써 두면, 그 안의 모든 대화가 같은 규칙으로 시작한다.
  • 지침은 "친절하게"처럼 확인할 수 없는 말이 아니라, 답을 보고 지켰는지 확인할 수 있는 규칙이어야 한다. 줄마다 '확인 방법'을 붙인다.
  • 지침 예시(5줄): ① PRD 기준으로 답한다 ② 표로 먼저 보여 준다 ③ 숫자 옆에 출처, 모르면 '확인 필요' ④ PRD에 없는 기능은 제안으로만 ⑤ 화면을 고치면 바뀐 부분 3줄 요약
  • 안/밖 비교: 같은 질문을 프로젝트 안과 밖에서 보내 답의 차이 2개를 적는다. 밖의 답이 PRD를 아는 것 같으면 메모리가 섞인 것이니 메모리를 잠시 끈다.
  • 실험: 프로젝트 안에서 "표 없이 길게 써 줘"라고 요청한다. 지침은 기본값이지 잠금장치가 아니다.

SESSION 5 · 메모리와 예약 작업 (15:20–16:30) [교안]

  • 메모리는 날짜·숫자를 정확히 기억한다는 보장이 없다. 날짜·숫자는 PRD 자료에서 확인한다.
  • 예약 작업 명세서 6항목: 작업 이름 / 언제 / 할 일 / 입력 자료 / 결과 받는 곳 / 멈출 방법
  • 예약 작업은 유료 플랜에서만 쓸 수 있고, 종료일 설정이 없어서 끝낼 날 직접 일시정지·삭제해야 한다. (교안이 인용한 클로드 공식 도움말 기준, 2026-11-03 시점)
  • 교안 예시: "연말 이벤트 아침 점검", 평일 오전 9시 KST, 12월 16일 아침에 직접 일시정지 → 멈출 날을 달력에 적기
  • 프롬프트에 "빠진 정보가 있으면 먼저 질문해"를 넣으면 잘못된 예약이 바로 만들어지는 일을 막는다.

SESSION 6 · 클로드 인 크롬 시연 보고 맡길 일 고르기 (16:30–17:10) [교안]

  • 오늘은 설치 없이 강사 화면으로만 봤다. 설치 실습은 이후 수업.
  • 권한 모드 3가지: 동작마다 허락 / 안전 검사 후 자동 진행 / 검사 없이 진행(완전히 믿는 일에만)
  • 어떤 모드에서도 묻는 동작: 민감한 정보 입력, 파일 다운로드, 권한 부여, 권한 설정 변경
  • 아예 하지 않는 동작: 결제·금융 거래, 계정 만들기, 카드·신분증 정보 처리, 영구 삭제, 시스템 파일 수정, 이메일·웹 페이지 속 지시 따르기
  • 판정 기준: 되돌릴 수 있는가 → 맡김 / 멈춤(내가 확인 후 진행) / 안 맡김
  • 성공 기준: 판정표 4줄에 '안 맡김'과 '멈춤'이 각각 1개 이상

3. 내 실습 — 올리브영 앱 구매 흐름 [실습]

교안의 셀렉트마켓 예시 대신 올리브영 온라인몰 선크림 구매를 주제로 작업함. 아래 내용 중 앱에서 직접 확인된 것은 "본인 인증이 없다"는 점뿐이고, 나머지 화면명·버튼 이름·시스템 처리·메뉴 위치는 [추정] 이다.

3-1. 성공 시나리오 5차 (사용자 행동 + 시스템 처리, 19단계)

No.시나리오
1사용자는 떨어진 선크림을 사려고 올리브영 앱을 실행해 홈 화면을 확인한다.
2사용자는 홈 화면 상단 검색창에 '선크림'을 입력해 검색한다.
3시스템은 입력한 검색어와 맞는 상품을 찾아 검색 결과 화면에 보여 준다.
4사용자는 검색 결과 화면에서 리뷰와 가격을 비교해 마음에 드는 상품을 선택한다.
5사용자는 상품 상세 화면에서 용량, 가격, 리뷰를 확인한다.
6사용자는 상품 상세 화면에서 상품을 장바구니에 담는다.
7시스템은 선택한 상품을 사용자의 장바구니에 저장한다.
8사용자는 장바구니 화면에서 수량과 상품 금액을 확인한다.
9사용자는 장바구니 화면에서 주문 버튼을 눌러 주문/결제 화면으로 이동한다.
10사용자는 주문/결제 화면에서 보유한 쿠폰을 선택해 적용한다.
11시스템은 쿠폰의 사용 조건을 확인하고 할인 금액을 반영해 최종 결제 금액을 다시 계산한다.
12사용자는 주문/결제 화면에서 포인트 사용 금액을 입력해 적용한다.
13시스템은 사용 가능한 포인트인지 확인하고 최종 결제 금액에 반영한다.
14사용자는 주문/결제 화면에서 배송지가 집 주소와 맞는지 확인한다.
15사용자는 주문/결제 화면에서 결제 수단을 선택해 결제한다.
16시스템은 결제 수단 회사에 결제 승인을 요청하고 승인 결과를 받는다.
17시스템은 승인이 되면 주문 정보를 서버에 저장하고 상품 재고를 차감한다.
18시스템은 주문 완료 화면에 주문번호와 도착 예정일을 보여 준다.
19사용자는 주문 완료 화면에서 도착 예정일을 확인한다.

버전 이력: 3차(13단계, 본인 인증 줄 포함) → 4차(12단계, 본인 인증 삭제) → 5차(19단계, 시스템 처리 7줄 추가)

약점·리스크

  • 4번(비교+선택), 15번(수단 선택+결제)은 행동이 둘로 보여 교안의 "한 줄에 행동 하나" 기준으로 쪼개라는 지적을 받을 수 있다.
  • 19단계가 교안 예시(9단계)보다 길다. 수업에서 허용하는 길이인지는 확인 불가. 줄인다면 포인트(12·13번)가 가장 자연스러운 후보.
  • 시스템 줄 7개(3, 7, 11, 13, 16, 17, 18번)는 쇼핑앱 일반 구조에 기댄 추정. 특히 재고 차감 시점은 모른다.
  • 로그인 시점을 모른다. 1번에 로그인을 넣지 않았다.
  • 실패·예외 시나리오는 아직 작성하지 않았다. 번호가 바뀔 때마다 실패 케이스 번호를 다시 맞춰야 한다.

  • 검색으로 확인된 것: 앱에 바코드 스캔, 주변 매장 조회, 선물하기, 상품평 사진 첨부, 1:1 문의 기능이 있다는 점까지.
  • [추정]: 메뉴 위치, 화면 이름, Depth 계층 전부. 바코드 스캔·매장 찾기를 홈 바로 아래에 둔 것은 근거 없음. 장바구니를 Depth2에 둔 것도 추정.
  • [주의] 오늘드림 설명은 2019년 기사에 근거해 현재 서비스와 다를 수 있음.
  • 23개 중 시나리오와 무관한 화면(오늘드림, 선물하기, 고객센터 등)이 절반 가까이라, 줄이라는 피드백을 받을 수 있음. 5단계 허용 여부도 모름.

  • 확인된 것: 가상 브라우저(jsdom)로 동작·글자 내용을 시험했고 자바스크립트 오류는 없었다.

  • 배운 점: 클로드 디자인 캔버스는 한 보드 안에서 상태가 바뀌는 구조라, 스켈레톤(1.2초), 담기 알림(2.6초), 승인 대기(약 3.5초) 같은 중간 화면은 순간적으로 지나가 따로 볼 수 없었다. 해결책으로 A(상태별 정지 화면 보드)와 B(화면 바로가기 버튼)가 제시됐다. 이후 스켈레톤 시안을 별도 파일로 만들어 보완했다.

4. 이번 작업에서 배운 점 (정리자 관찰)

  1. AI가 앱에 없는 내용을 넣을 수 있다. 시나리오 3차에 "본인 인증" 줄이 들어갔으나 실제 올리브영에는 없어 삭제했다. 내가 준 예시 문장을 앱의 사실처럼 쓴 오류였다. → 앱 대조는 필수.
  2. 번호가 바뀌면 연결된 표가 같이 어긋난다. 시나리오 단계가 늘면 실패 케이스 번호도 다시 맞춰야 한다.
  3. '확인 필요'를 남기는 습관이 실제로 필요했다. 시스템 처리·IA 계층은 전부 추정이어서 시트에 "확인 필요" 표시를 해 두었다.
