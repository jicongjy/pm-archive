1. 오늘의 한 줄 요약

AI(LLM)는 없는 책, 저자, 링크를 그럴듯하게 지어낼 수 있으므로 기획자는 틀리면 안 되는 값을 AI에게 맡기지 않는 화면을 설계해야 합니다. 오후 슬랙 수업에서는 같은 감정 책 추천 프로토타입을 기준으로 입력, 처리, 출력 정리, 요구사항 작성, 테스트 보고서, ASIS와 TOBE 도식을 연습했습니다.

2. 교안 기준 학습 내용

오늘의 단어

단어뜻

SESSION 1. LLM이 무엇이고 어디서 틀리나

  • LLM은 사용자가 감정을 저마다 다르게 적어도 뜻을 읽고 어울리는 답을 글로 만들어 줍니다. 규칙 방식은 감정 낱말마다 책 목록을 미리 짝지어 둬야 합니다.
  • 책 추천에서 틀릴 수 있는 곳은 세 가지입니다. 없는 책을 지어냄, 있는 책에 다른 저자를 붙임, 상품 번호를 지어낸 링크를 만듦.
  • 환각을 줄이는 방법으로 공식 문서는 "모르면 모른다고 말해도 된다고 허락하기"와 "근거를 함께 내게 하기"를 듭니다.
  • 실습: 클로드의 웹 검색을 끄고 책 3권과 YES24 링크를 받아, 링크를 하나씩 눌러 제목과 저자가 같은 책인지 확인하는 표(링크 확인표 3줄)를 만듭니다.

SESSION 2. 책 추천 화면 기획하기

  • 링크는 AI가 아니라 코드가 만듭니다. YES24 검색 주소(query= 뒤에 제목)를 코드가 붙이면 상품 번호가 필요 없고, 책이 없으면 검색 결과가 비어 보여서 사용자도 바로 알 수 있습니다.
  • 역할 분담: AI는 감정을 읽고 책 제목, 저자, 추천 이유를 고르고, 코드는 검색 주소를 만들어 카드에 넣고, 사용자는 YES24에서 실제 책을 확인합니다.
  • AI가 돌려줄 답은 JSON(books 안에 title, author, reason)으로 정해서 코드가 칸마다 꺼내 카드에 넣게 합니다.
  • 기획표 7줄: 입력, AI에게 맡길 일, AI가 지킬 규칙, 코드가 할 일, 카드 한 장, 그대로 둘 것, 만들지 않을 것.
  • encodeURIComponent는 한글이나 띄어쓰기가 든 제목을 주소에 넣을 수 있는 글자로 바꾸는 코드입니다.
  • 오늘 앱은 YES24 페이지를 모으지 않고, 사용자가 누를 링크만 만듭니다(화요일 robots.txt 학습과 연결).

SESSION 3. Hello 페이지에 책 추천 붙이기

  • 지난주 금요일에 만든 AI 스튜디오 Hello 앱에 "오늘의 감정" 입력칸과 [책 추천받기] 버튼을 더해, 책 3권 상품 카드가 나오게 만듭니다.
  • 감정 세 가지(설렘, 지침, 내가 고른 감정)로 눌러 보고, [YES24에서 보기] 주소가 검색 주소로 시작하는지, 기존 이름 입력과 Firestore 저장이 그대로인지 확인합니다.
  • 누를 때마다 무료 한도를 쓰므로 감정마다 한 번씩만 누릅니다.
  • 막힐 때: 카드가 안 나오면 오류 문장을 대화창에 붙여 고치게 하고, 주소에 상품 번호가 들어 있으면 AI가 링크를 만든 것이므로 코드가 검색 주소를 만들게 고치게 합니다.

SESSION 4. 추천이 진짜인지 확인하고 고치기

  • 추천된 책 9권을 YES24 검색 결과와 견주어 "검색 결과에 있나, 저자가 같나"를 O/X로 확인합니다.
  • 규칙 고치기: "실제로 있는지 확실한 책만 골라. 확실한 책이 3권이 안 되면 확실한 만큼만 답해도 돼. 저자를 모르면 그 책은 빼."를 더하고, 카드가 3장보다 적으면 안내 한 줄을 보여 줍니다.
  • "꼭 3권을 채워 줘"라고 하면 AI가 빈칸을 채우려고 책을 지어낼 수 있으므로, 진짜인 것이 더 중요하면 개수를 줄여도 된다고 허락합니다.
  • 고치기 전과 후의 확인표를 견주어 봅니다.

SESSION 5. 무료 한도와 API 키는 어디에 있나

  • AI 스튜디오 Build로 만든 앱은 API 키를 서버 쪽 비밀값(Secret)으로 두기 때문에, 사용자 화면 코드에 키가 들어가지 않습니다.
  • 한도 단위는 분당 요청 수(RPM), 분당 토큰 수(TPM), 하루 요청 수(RPD)이고, 한도는 키가 아니라 프로젝트마다 적용됩니다.
  • 공유한 앱을 다른 사람이 쓰면 그 호출도 내 사용량에 쌓입니다.
  • 가격표에 무료 등급은 "제품 개선에 사용됨"으로 적혀 있어서 입력칸에 개인정보를 넣지 않습니다.
  • 무료 등급에서는 제미나이의 구글 검색 확인 기능을 쓸 수 없어서, 사람이 YES24에서 확인하는 단계가 필요합니다.
  • 유료로 바꾸려면 결제 계정을 연결하고 최소 5달러를 미리 충전해야 합니다. 오늘은 결제를 연결하지 않습니다.

오늘의 규칙

  1. LLM은 없는 책, 저자, 링크를 그럴듯하게 지어낼 수 있다.
  2. 틀리면 안 되는 값(링크, 상품 번호)은 AI에게 맡기지 않고 코드가 만든다.
  3. AI의 답은 JSON처럼 칸을 정해 받으면 화면에 나눠 넣기 쉽다.
  4. 개수를 채우는 것보다 진짜인 것이 중요하면 "확실한 만큼만 답해도 돼"라고 허락한다.
  5. API 키는 화면 코드가 아니라 서버에 둔다. 무료 등급에는 개인정보를 넣지 않는다.

3. 슬랙 기준 수업 내용 (강사 안내)

오전

  • 오늘 주제는 AI를 붙여 보는 최소한의 웹페이지 기획과 구현입니다. 구글 AI 스튜디오를 사용하고, 볼트에서 깃허브 레포를 import해서 이어서 작업합니다. 클로드 유료 버전 안에서 내장 클로드 API를 활용한 수업 진행도 가능합니다.
  • 실습1: 감정 키워드를 입력하면 맞는 책 3가지를 추천하는 텍스트 기반 프로토타입을 만듭니다.
  • 결과물을 입력, 처리, 출력 관점에서 분리해서 서술합니다.
  • 실습2: 입력과 출력 부분을 바꿔서 다른 UX/UI 프로토타입으로 만듭니다.
  • 프로토타입의 로직을 AI에게 물어보고, AI가 붙지 않은 부분이 있다면 AI를 붙인 버전을 만들어 탭1과 탭2로 분리해 차이를 봅니다.
  • 탭2(AI 적용 버전)만 단독 HTML 파일로 받아서 코드 안에서 차이를 직접 찾아봅니다.

기획자 관점으로 돌아오기

  • 탭2의 AI 서비스를 개선하려고 할 때, 개발자에게 줄 사용자 스토리(요청사항)를 2~3개 정리해 봅니다.
  • 요구사항 작성법: AI가 하는 일 한 문장(예: 고객 문의를 6개 유형으로 분류한다), 사용자와 사용 맥락, 입력(무엇이 들어오나)과 출력(무엇을 돌려주나), AI가 하지 않을 일과 사람에게 넘길 조건.
  • 더 간단히 하면 기획자가 요구사항을 전달할 때 기준은 입력, 처리, 출력입니다.
  • 실습1: 프로토타입을 테스트해서 나온 문제와 해결방안을 표로 정리하고, 내 요구사항에 맞는 성공 예시를 포함해 개발자에게 전달할 내용을 작성합니다. 이 목록은 실제 기획서에 들어갈 수 있다고 하셨습니다.

오후

  • 실습2: 원하는 프로토타입으로 개선(개발자 입장에서 구현).
  • 실습3: 테스트까지 진행하고, 테스트가 끝나면 AI에게 직접 테스트해 보라고 하고 테스트 보고서도 요청합니다.
  • 실습3-1: 기능별로 테스트가 잘 되었는지 검증 결과를 엑셀 표로 정리.
  • 실습3-2: UX/UI 확인을 위해 테스트 결과를 유저플로우(화면 중심)로 직접 캡처해서 정리. 실무자가 테스트할 항목을 나열하고 결과를 쓰는 예시와 보고서 예시가 공유되었습니다.
  • 개선된 버전 프로토타입을 만들고 프롬프트로 질문합니다: 프롬프트가 개선되었나, AI가 동작하는 기능이 아닌 다른 부분이 기능적으로 개선되었나, 디자인이 개선되었나.
  • ASIS와 TOBE를 도식으로 구분하고, 그 안에서 AI가 어떤 처리를 하는지 구분해서 도식화합니다. 지금은 역기획이지만 실전에서는 기획자가 기획서에 먼저 정의해서 전달할 수 있다고 하셨습니다. 수강생 보고서의 도식은 플로우차트 정석으로 제시되었습니다.
  • API 키 받기: 메뉴가 안 보이면 platform.claude.com/settings/keys 로 접근합니다. 코드의 비어 있는 API 키 자리에 제미나이 샘플 API를 붙이거나 직접 생성해서 추가하고, 안 되면 내가 클로드 API 키를 입력합니다.
  • 마지막 질문: "개발자 관점에서 어떤 모델이 성능이 가장 좋은가요?" (슬랙에 답 기록이 없어 미기입)
